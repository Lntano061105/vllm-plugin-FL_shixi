## v1（尝试优化 —— 无收益，已回退）

### 改动内容（仅 host 侧，不碰 kernel 与数值语义）

1. `LogTilingResults()` 中 4 条 `OPS_LOG_I` 用 `#if defined(ADD_RMS_NORM_BIAS_TILING_LOG)` 屏蔽
   （默认关闭，需要调试时编译期打开）
2. tiling 入口的 `OP_LOGI("Tiling4AddRmsNormBias", ...)` 同样屏蔽
3. `getPerformanceFlag(uint32_t, gert::Shape, gert::Shape, uint32_t)` → shape 参数改 **const 引用**

假设：tiling 每次调用都做字符串格式化与日志派发，构成可观 host 开销。

### 验证结果

| 项 | 结果 |
|---|---|
| 编译 | ✅ SUCCESS |
| 正向 24 组 | ✅ `ALL TESTS PASSED` |
| 异常用例 | ✅ 8 PASS / 2 FAIL（与 v0 一致） |

按"测瓶颈 → 挑技法 → 实测无效即回退"的纪律，v1 不予保留，源码与已安装产物均回退到 v0。

## v2（规范修复 —— 保留，但无性能收益）

### 改动内容（仅 1 文件，+10/−3）

```cpp
- constexpr size_t sysWorkspaceSize = 16 * 1024 * 1024;   // 魔法数字
- constexpr size_t usrSize = 256;                          // 虚设：kernel 从不使用
+ auto ascendcPlatform = platform_ascendc::PlatformAscendC(context->GetPlatformInfo());
+ uint32_t sysWorkspaceSize = ascendcPlatform.GetLibApiWorkSpaceSize();  // 官方 API
  size_t* currentWorkspace = context->GetWorkspaceSizes(1);
- currentWorkspace[0] = usrSize + sysWorkspaceSize;
+ currentWorkspace[0] = sysWorkspaceSize;
```

### 依据（查官方 API 文档 + 代码实测）

1. 官方 `GetLibApiWorkSpaceSize` / `SetSysWorkSpace` 文档明确：
   **系统 workspace 大小必须查询、不能硬编码**；且系统 workspace 是给
   **Matmul 等高阶 API** 用的，本算子只用基础矢量 API
2. `GetUserWorkspace` 在 8 个 kernel 文件中**出现 0 次**；`GENERAL_OP_IMPL` 宏
   甚至不把 workspace 指针传给 kernel → 256 B 用户 workspace 确属虚设

### 实测结果 —— 假设被官方 API 否掉

打印 `GetLibApiWorkSpaceSize()` 实际返回值：

```
[INFO] [add_rms_norm_bias_tiling.cpp:379][OP_TILING][Custom][SetWorkspaceSize]
       "GetLibApiWorkSpaceSize() = 16777216 bytes (user workspace unused)"
```

**16777216 = 正好 16 MiB，与原硬编码值完全相同。**

⇒ 系统 workspace **不是浪费**，是框架确有要求；`EXEC_NPU_CMD` 的
`at::empty({16 MiB})` 在 v2 下**照旧发生**。

| 指标 | v0 | v2 | 判定 |
|---|---|---|---|
| custom/native host 比值均值 | 1.531 | 1.516 | −1.0%，**噪声内** |
| 绝对差距（漂移校正后） | 16.8 µs | ~18.2 µs（校正预期 18.95） | **无改善** |
| 正向 24 组 | PASSED | PASSED | ✅ |
| 异常用例 | 8/2 | 8/2 | ✅ |

**处置：保留**（去掉魔法数字，命中管理员"避免硬编码"要求；去掉虚设的 256 B），
但**明确标注：这是规范修复，不是性能优化**。commit message 已如实写明 "Measured effect: none"。

### 附带发现：日志的真实成本

在 INFO 级别下从 plog 时间戳测得：`SetWorkspaceSize` + 4 条 `LogTilingResults`
共耗时 **19 µs / 15 µs**，即**一条带格式化的 `OPS_LOG_I` 约 4-5 µs**。

**这给 v1 的负结果补上了机理证据**：默认日志级别是 `ERROR`（技能铁律 35），
这些 `OPS_LOG_I` 被级别检查短路，**格式化根本不执行** → v1 改它当然无用。

## v3（tiling 插桩计时 —— 测量中）

目的：host 差距中**唯一属于本算子**的部分是 tiling 回调，需测出它的真实成本，
以给出"host 侧还能优化多少"的**硬上界**。

插桩方式（纯测量，无行为变更）：
- 计时窗口**刻意排除所有日志调用**（否则会把 4-5 µs/条的日志开销算进来）
- 分段测量：`total` / `check`（`CheckInputOutputShape`）/ `body`（其余计算）
- 结果经 `OPS_LOG_I("TILING_TIMING ...")` 输出，从 plog 解析

**判据**：测得的 tiling 耗时即为 host 侧可优化空间的**上界**。
若为 µs 量级 → 不值得继续；若为 10 µs 量级 → 值得优化。

## 瓶颈定位结论（本轮最重要的产出）

| 量 | 数值 | 来源 |
|---|---|---|
| 我们 kernel 单次耗时 | **~2.74 µs** | Profiler `op_statistic.csv`（27B，32 tokens） |
| host 侧派发差距 | **~16 µs** | 本次分解实测 |
| 单次调用总差距 | ~25-30 µs | 微基准 |
| 模型每步耗时（35B eager） | ~250 ms | 4-Baseline 实测 |

**结论：差距的 ~100% 在 host 侧（aclnn 两段式派发 + aclTensor 描述符构造 + 3 次输出张量分配），
不在 kernel。** 即使把 kernel 优化到 0，也只省 2.74 µs；相对模型每步 250 ms 占比 <0.001%。

### 为什么改 kernel 没有收益

- 结构原因：自定义算子走 `aclnnXxxGetWorkspaceSize` + `aclnnXxx` 两段式，每次都要构造 7 个
  aclTensor 描述符并跑一次 host tiling；原生 `torch_npu.npu_add_rms_norm` 是内置算子，派发路径更短。
- 这不是 kernel 代码质量问题，**换任何 kernel 实现都改变不了**。

### 后续可探索方向（未验证，仅记录）

1. **减少输出分配**：`at::empty` 每次 3 次（y/rstd/x），其中 rstd 在 Gemma 路径被丢弃 →
   若能让 rstd 可选（def.cpp + kernel + tiling 联动改造），可省一次分配，但属较大改动、需重新验证
2. **tiling 常量缓存**：`GetCoreNumAiv()`/`GetCoreMemSize()` 已通过 compileInfo 缓存，暂无进一步空间
3. **换更短的派发路径**：需框架侧支持，非本算子可独立完成
